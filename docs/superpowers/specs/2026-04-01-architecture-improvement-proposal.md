# 数学知识演化系统（Math-IM-Book）架构优化与改进建议书

**版本：** 1.0  
**日期：** 2026-04-01  
**状态：** 提议中  

---

## 1. 核心需求回顾与对标

根据 `spec/plan/System_design.md` 的愿景，本系统应是一个“以对话驱动、以知识节点沉淀、可分叉演化、面向数学书稿长期构建的知识系统”。

### 当前实现与愿景的差距：
*   **知识沉淀的“空心化”**：愿景要求“回答属于 Chat，事实属于 Knowledge”，但当前实现中，生成的 `KnowledgeNode` 往往只是包含问题摘要的“占位符”，真实的数学推导和知识细节留在对话历史中，未能真正“结晶”为高质量的知识节点。
*   **规划层的“机械化”**：愿景中的 Agent Planning Layer 应具备意图识别和知识缺口诊断能力，而目前的 `QuestionPlanner` 采用基于关键词匹配的启发式得分，无法处理复杂的数学语义逻辑。
*   **符号一致性的“扁平化”**：虽然引入了 `Symbol Registry`，但缺乏层级作用域管理，导致在多分支（Fork）场景下，全局约定与局部定义容易冲突或丢失。
*   **整理机制的“物理化”**：`/compact` 目前更多是结构上的归档和摘要，缺乏语义层面的知识合并与重构，未能实现从“探索态”到“书稿态”的本质飞跃。

## 2. 现状问题深度诊断

### 2.1 逻辑层：启发式规划器（QuestionPlanner）的局限
目前的 `QuestionPlanner` 依赖关键词频率（TF-like）计算节点相关性。
*   **风险**：数学问题往往具有高度的语义重叠（如“线性空间”与“向量空间”），仅靠关键词无法区分“需要新定义”、“需要扩展已有定义”还是“需要证明一个已知命题”。
*   **天花板**：它无法识别用户的隐式意图（如：用户在纠正一个之前的符号错误），导致系统无法主动建议 `align_symbols` 等高级动作。

### 2.2 存储层：占位符节点（Placeholder Nodes）的弊端
当前 `KnowledgeOrchestrator` 在扩展知识时，先创建一个空节点，再由 LLM 生成回答。
*   **问题**：生成的回答文本（`assistant_text`）未回填至节点的 `detail` 字段。
*   **后果**：知识库充斥着标题为“定义 X”但内容为“这是为了回答 Y 问题而创建的草稿”的空壳。这破坏了知识库作为“书稿长期记忆”的价值。

### 2.3 符号层：缺乏作用域管理（Scope Management）
当前的 `SymbolRegistry` 只是将选定节点的符号简单合并。
*   **风险**：在数学研究中，同一个符号 $k$ 在全局可能代表域，但在局部引理中可能代表索引。缺乏 `Global -> Session -> Node` 的继承与覆盖机制，会导致 LLM 生成的内容在符号使用上出现低级错误或混淆。

### 2.4 交互层：Fork 与 Compact 的逻辑隔离
*   **Fork 问题**：当前的 Fork 仅仅是创建新会话，未能深度克隆必要的语义切片。
*   **Compact 问题**：目前的压缩是“物理删除/隐藏”，而不是“逻辑重构”。它没有利用 LLM 对多个相关节点进行合并、去重和提纯，导致知识库随着时间推移变得碎片化。

## 3. 改进方案设计（核心部分）

### 3.1 LLM-First 规划器重构
将 `QuestionPlanner` 升级为基于 LLM 的语义规划器。
*   **Agent Action Contract**：规划器输出标准的 JSON 协议，包含：
    - `intent`: (REFINE_EXISTING | EXPLORE_NEW | RECONSTRUCT_SYMBOLS | COMPACT_SUGGESTION)
    - `knowledge_gap_analysis`: 识别当前上下文缺失的确切定义或定理。
    - `action_plan`: 一系列原子操作指令。
*   **优势**：利用 LLM 的逻辑推理能力，精准判断是否需要 Fork 分支或合并旧知识。

### 3.2 双阶段生成流程（Crystallization Pattern）
改变“先占位后回答”的模式，采用“生成即沉淀”：
1.  **阶段一：知识结晶（Knowledge Synthesis）**：LLM 首先根据问题和上下文，生成/更新受符号约束的 `KnowledgeNode`（包含 Title, Summary, Detail, Symbols）。
2.  **阶段二：对话响应（Chat Rendering）**：基于阶段一生成的“书稿态”节点，LLM 再次润色生成“对话态”的回答。
*   **结果**：确保每一次高质量的对话都会在磁盘上留下一个高质量的 Markdown 知识节点。

### 3.3 层次化符号注册表（Hierarchical Symbol Registry）
实现类似编程语言作用域的符号管理：
*   **Global Scope**：定义全书通用的符号（如 $\mathbb{R}, \mathbb{C}$）。
*   **Session Scope**：当前对话分支的约定。
*   **Node Scope**：特定定义或定理内部的局部符号。
*   **机制**：查询符号时自下而上搜索，生成内容时注入全路径符号约束。

### 3.4 实质性 Compact 机制
引入 **Semantic Merge** 流程：
1.  **节点聚类**：利用 LLM 识别语义重复或高度相关的碎片节点。
2.  **内容提纯**：将 3-5 个碎片节点合并为一个完整的“汇总节点（Summary Node）”，并自动更新所有引用（Reference）指向新节点。
3.  **冲突消解**：在合并过程中，由 LLM 统一术语和符号表达，从“草稿”升级为“书稿”。

## 4. 头脑风暴与创新点

### 4.1 引入“证明辅助（Proof Assistant）”思路
*   **LaTeX 语法校验**：在保存节点前，自动调用外部工具（如 `chktex` 或轻量级 parser）验证公式闭合性。
*   **符号追踪**：自动提取节点内的 LaTeX 公式，对比 Symbol Registry，若出现未定义符号则标记警告。

### 4.2 “待沉淀草稿（Pending Drafts）”的交互闭环
*   **设计**：前端增加“草稿箱”区域。系统生成的节点初态为 `status: pending`。
*   **闭环**：用户可以在 UI 上对草稿进行“一键修正”或“批准入库”。只有批准后的节点才会参与未来其他 Session 的 Context 组装。

### 4.3 自动生成的“桥接节点（Bridge Nodes）”逻辑
*   **场景**：当系统发现用户跳跃式提问时（例如从定义 A 直接问到应用 C，中间缺失引理 B）。
*   **逻辑**：规划器主动识别断层，生成一个 `type: bridge` 的节点，负责连接 A 与 C 的逻辑链路。

## 5. 分阶段实施路线图

### 第一阶段：V1.5 核心结晶化（1-2 周）
*   **任务**：
    1.  重构 `KnowledgeOrchestrator`，实现双阶段生成逻辑，确保回答回填到 `KnowledgeNode.detail`。
    2.  升级 `QuestionPlanner`，引入简单的 LLM Intent API。
*   **目标**：解决“知识库空心化”问题。

### 第二阶段：V2.0 智能演化增强（2-4 周）
*   **任务**：
    1.  实现层次化 `SymbolRegistry`。
    2.  开发 LLM 驱动的 `/compact` 逻辑，支持节点合并。
    3.  前端增加“草稿审核”交互。
*   **目标**：实现真正的“书稿态”重构能力。

### 第三阶段：V2.5 严谨性与自动化（1 个月+）
*   **任务**：
    1.  集成 LaTeX 校验工具。
    2.  实现自动桥接节点探测。
    3.  支持多格式（PDF/EPUB）导出。
*   **目标**：系统具备生产级数学书稿构建能力。
