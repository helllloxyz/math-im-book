# Code Review Report: Math-IM-Book Implementation Audit

**Date:** 2026-04-01  
**Status:** Audit Complete - Action Required

## 1. Executive Summary
The current implementation has established a solid foundation for the Chat-Knowledge dual-core architecture. The basic mechanics of sessions, forks, and markdown-based knowledge storage are functional. However, there are significant deviations from the "LLM-driven" and "Mathematical Consistency" goals outlined in the design documents. The system currently relies heavily on heuristic rules rather than semantic planning.

## 2. Critical Findings

### 2.1 Planning Layer: Heuristic vs. Semantic
*   **Design Goal:** The LLM should be responsible for intent recognition and task planning (`Agent Action Contract`).
*   **Current Implementation:** `QuestionPlanner` uses keyword scoring and regex to decide between reusing a node or drafting a new one.
*   **Impact:** This limits the system's ability to handle complex or nuanced mathematical queries that don't match keywords but are semantically related.

### 2.2 Knowledge Precipitation: Placeholder Nodes
*   **Current Implementation:** When a new knowledge node is "drafted," the system creates a markdown file with placeholder text (e.g., "Title is newly drafted to answer: Question").
*   **Issue:** The actual "smart" content generated by the LLM is stored in the Chat Session history (`assistant_text`), but the saved Knowledge Node remains a nearly empty shell.
*   **Impact:** Future lookups of that node will provide no actual mathematical detail to the LLM context, breaking the long-term knowledge accumulation goal.

### 2.3 Draft Management: Immediate Realization
*   **Design Goal:** `Pending Draft` should represent knowledge gaps that the user can manage or refine.
*   **Current Implementation:** The orchestrator immediately saves the first draft request as a node. Other requests in the list are ignored.
*   **Impact:** No opportunity for user-in-the-loop validation of the knowledge structure. The knowledge base grows "randomly" based on the first item in a heuristic list.

### 2.4 Symbol Registry: Passive Conflict Detection
*   **Design Goal:** A first-class object for constraining generation and managing scope (Global/Theme/Local).
*   **Current Implementation:** `SymbolRegistry` is a utility for detecting string mismatches during context building. It has no concept of scopes or hierarchical inheritance.
*   **Impact:** Mathematical consistency relies entirely on the LLM's adherence to a prompt string, with no structural enforcement or scope management.

### 2.5 `/compact` Mechanism: UI-Only Refactoring
*   **Design Goal:** A mechanism to refactor "exploration-state" content into "book-state" content (merging nodes, aligning symbols on disk).
*   **Current Implementation:** The `/compact` command generates a summary message in the chat and updates the session's context filters. It does **not** modify or merge the underlying markdown nodes.
*   **Impact:** The knowledge base continues to accumulate fragmented and exploration-heavy nodes without ever being "distilled" into a coherent book structure.

## 3. Potential Issues & Risks

1.  **Context Bloat:** Because nodes are not actually refactored by `compact`, the "Summary Context" will eventually become cluttered with redundant or low-quality summaries of placeholder nodes.
2.  **Symbol Drift:** Without scope management, local symbol definitions in one branch may pollute the global understanding or cause avoidable conflicts when merging branches.
3.  **Content Disconnect:** The "Reader" panel (showing nodes) will appear empty or useless because the nodes only contain placeholders, while the "Chat" panel contains all the value.

## 4. Recommendations (Unrefined)

1.  **Refactor `QuestionPlanner`:** Transition to an LLM-based planning prompt that returns a structured `AgentAction` JSON.
2.  **Robust Node Generation:** Modify `KnowledgeOrchestrator` to perform a two-step generation when expanding: 
    *   Step A: Generate the content of the Knowledge Node(s) with formal mathematical rigor.
    *   Step B: Generate the conversational assistant response based on those nodes.
3.  **Implement Pending Draft Workflow:** Allow the backend to return `PendingDraft` objects without immediately saving them, and add frontend support for "Commit Draft to Knowledge Base."
4.  **Enhance Symbol Registry:** Introduce a `SymbolScope` model and allow `SymbolRegistry` to handle inheritance (Global -> Session -> Node).
5.  **True Compaction:** Implement a task that allows the LLM to rewrite and merge multiple markdown files into a single "Summary" or "Chapter" node.

## 5. Implementation Gaps in Frontend
*   No visual indication of "Summary" vs "Detail" context in the chat view.
*   Missing "Pending Drafts" management interface.
*   The "Book Outline" is a flat list of nodes rather than a hierarchical structure as suggested by the `parent_id` field.
