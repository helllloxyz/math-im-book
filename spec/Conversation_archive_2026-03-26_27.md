# 对话归档：数学知识演化系统设计讨论

## 1. 归档目的

本文档用于保存本轮关于“数学知识演化系统”的核心对话内容，方便后续回看。

归档重点不是逐字转录全部聊天内容，而是保留：

1. 用户的原始想法和关键判断
2. 对系统方向产生影响的关键问答
3. 设计收敛过程中的主要结论
4. 已经落盘的正式文档与它们的来源关系

## 2. 对话背景

用户指出当前仓库“生成书籍”的逻辑偏自上而下，希望保留大的自上而下主线，但不再一次性生成，而是在与用户的交互过程中逐步生成内容。

核心新方向包括：

1. 知识结构像树一样不断分叉
2. 对话驱动知识生长
3. 需要维护 context
4. 可以借鉴 `skill markdown` 的管理方式
5. 数学场景必须重视符号和定义一致性
6. 希望有 `/compact` 之类的自动整理能力
7. 前端交互要兼顾网络状知识文本和命令行式交互逻辑

## 3. 用户初始想法摘录

### 3.1 从“一次生成”转向“交互式生长”

用户最早提出：

1. 当前仓库生成书籍的逻辑偏自上而下
2. 希望改成仍有主线，但不是一次性生成
3. 更像与用户交互过程中逐渐生成
4. 先列主要思想，后续根据用户问题选择生成方向
5. 整体像一棵树，不断分叉

这是整个系统设计的出发点。

### 3.2 Context 管理与 Markdown 管理

用户提出：

1. 知识之间联系广泛，因此生成过程中必须维护 context
2. 一个好的思路是参考 `skill` 的方式
3. 用 markdown 文件承载知识
4. 头部是简略描述
5. 不断卸载不需要的部分，加载需要的部分

由此引出了后续的：

1. 节点化知识管理
2. summary 驱动的上下文加载
3. detail 按需展开

### 3.3 数学特殊性：符号一致

用户明确指出：

1. 数学类内容需要考虑定义、符号和记号的一致性
2. 即使同一个模型可能比较一致，也不能完全依赖模型自然保持一致
3. 系统不能过于复杂，否则不够灵活智能
4. 可以考虑 `/compact` 指令来自动整理整个内容

这直接推动了后续 `Symbol Registry` 和 `/compact` 的设计。

### 3.4 前端交互问题

用户提出：

1. 需要参考好的前端交互设计
2. 一方面是网络状知识文本
3. 一方面是命令行式的交互逻辑

这导致后续设计中形成了：

1. 对话主导
2. 知识辅助
3. 分支可见

的三域界面模型。

### 3.5 新的总体原则

用户后来给出了更完整的一版想法：

1. 以对话为基础
2. 使用 agent 思路，维护 context = state + memory
3. context 中包含：
   - 符号表
   - markdown 表示的知识定义 list，树状层次结构
   - 当前激活的 chat 节点关系，因为会 fork
4. 用户提问后，系统先检查已有知识树
5. 如果已有知识足够，则直接拉取相关知识回答
6. 如果需要扩展知识树，则先生成一份清单，先生成相关内容并落盘，再回答问题
7. 历史对话保留，用于分析用户偏好
8. 可以开新对话
9. 核心是维护知识库，知识库最终像一份书籍文本
10. 回答问题时可以引用 markdown 中片段，避免重复
11. 用户可以选中内容继续问，选中内容问会自动 fork，避免上下文过大

这是后续正式设计的最核心需求来源。

## 4. 对系统定位的关键收敛

在对话中，系统先询问这次文档更偏：

1. MVP 产品设计
2. 完整系统设计
3. 前端/交互设计

用户选择：

`面向完整系统设计，实现细节可以先不用考虑。`

随后又针对系统核心对象进行了澄清。

### 4.1 关于“对话优先”还是“知识库优先”

系统曾提出三种可能：

1. 知识库优先
2. 对话优先
3. 双核心

用户回答：

`都重要，我感觉这两个不矛盾。`

于是系统收敛为：

`Chat` 和 `Knowledge Base` 双核心并列。

### 4.2 关于知识沉淀的默认节奏

系统提出三种主流程：

1. 先回答，按需沉淀
2. 先判断，再分流
3. 默认都沉淀

用户明确选择第二种，并补充了一个关键难点：

`系统先判断：已有知识就引用并回答；缺失知识就先生成待沉淀条目。`

并进一步指出：

`条目多细这个边界有点难点，如何引用才能更好的复用同时保持上下文连贯，summary + detail 超链的形式？`

由此引出：

1. `Pending Draft`
2. `summary + detail + hyperlink`
3. 节点拆分边界

### 4.3 关于知识粒度

系统提出三种粒度：

1. 原子粒度
2. 小节粒度
3. 混合粒度

用户回答：

`可以混合，重要的部分用原子粒度。`

于是正式设计中采用：

1. 原子节点
2. 汇总节点

并以“重要知识优先原子化”为原则。

## 5. 对 Chat/Fork、上下文与 agent 的关键收敛

在继续系统设计时，用户特别强调：

`希望多引入 LLM 的语义理解和 agent 的智能规划的特点，这样最灵活。`

围绕这一点，对话中形成了以下关键结论：

### 5.1 Chat 不是普通消息列表

Chat 被定义为：

1. 显式对话
2. 当前工作上下文
3. 会话状态
4. 隐式 agent 计划

也就是说，Chat 是一个语义工作流，而不是简单聊天记录。

### 5.2 Fork 的原则

对话中明确收敛出一句核心判断：

`Fork 继承的是语义起点，不继承全部消息。`

这句话成为后续设计中的重要原则。

### 5.3 上下文的定义

对话中将上下文从“装多少文本”提升为：

`激活的语义对象集合`

这直接支撑了后续的四层上下文设计：

1. Global Context
2. Session Context
3. Focused Context
4. Latent Context

### 5.4 LLM 的核心作用

在这一轮对话中，LLM 的定位被明确为：

1. 语义理解
2. 任务路由
3. 激活集规划
4. 回答组织
5. compact 时的语义归并和重写

而不是只做文本生成。

## 6. 对 Symbol Registry 与 /compact 的关键收敛

### 6.1 Symbol Registry

围绕数学场景，最终形成了一个很明确的判断：

1. 符号表必须是一等对象
2. 它负责约束生成、检测冲突、管理作用域
3. 要支持全局与局部例外，但例外必须显式声明

### 6.2 /compact

对话中，`/compact` 从最初的“自动整理整个内容”逐步收敛为：

1. 不是单纯压缩 token 的命令
2. 而是把探索态内容重构为书稿态内容的机制

它的职责包括：

1. 压缩非活跃上下文
2. 合并过碎节点
3. 统一符号和定义
4. 重排结构，让随机长出的内容回挂到更合理的主线

## 7. 对前端/交互模型的关键收敛

用户希望系统兼顾：

1. 网络状知识文本
2. 命令行式交互逻辑

基于此，对话中最终收敛出前端原则：

1. 不是复杂知识图谱平台
2. 也不是纯聊天窗口
3. 而是 `对话主导 + 知识辅助 + 分支可见`

推荐的三域界面模型为：

1. 中间主对话区
2. 左侧知识树/知识地图
3. 右侧引用预览/节点详情

同时命令被定义为增强层，而不是唯一交互层。

## 10. 本轮讨论中形成的关键设计结论

以下结论是本次对话里最核心、最值得后续反复回看的内容。

### 10.1 系统不是自动写书工具

它是一个：

`通过对话不断生长、整理、收束，最终演化成数学书稿的知识构建工具。`

### 10.2 双核心原则

1. `Chat` 负责探索、组织、解释、分叉
2. `Knowledge Base` 负责事实沉淀、复用和书稿结构

两者并列，不是主从关系。

### 10.3 回答与事实分离

对话中形成了重要原则：

`回答属于 Chat，事实属于 Knowledge。`

### 10.4 引用机制

系统不应默认拼全文，而应采用：

`summary + detail + hyperlink`

这既保证复用，也保持上下文连贯。

### 10.5 粒度策略

知识粒度采用混合模式，但重要知识必须支持原子化。

### 10.6 缺失知识时先分流

当知识不足时，不应直接无边界生成，而应：

1. 先识别知识缺口
2. 生成待沉淀条目
3. 再基于这些条目回答

### 10.7 Fork 原则

`Fork 继承语义起点，不继承全部历史消息。`

### 10.8 上下文原则

上下文不是文本堆，而是激活的语义对象集合。

### 10.9 LLM 的定位

LLM 的核心价值在于：

1. 理解
2. 路由
3. 规划
4. 编排
5. 整理

而不是只生成文字。

### 10.10 /compact 的角色

`/compact` 是知识重构机制，而不是普通清理命令。
