# 数学知识演化系统实施阶段划分

## 1. 文档目标

本文档基于 [`System_design.md`](./System_design.md) 和 [`MVP_scope.md`](./MVP_scope.md)，将产品落地顺序收束成清晰的阶段划分。

目标不是展开工程实现，而是回答四个问题：

1. 第一版产品应该先做什么
2. 哪些能力必须晚一点做
3. 每个阶段验证什么
4. 各阶段之间的依赖关系是什么

本文档强调：

`先跑通核心闭环，再增强智能性，再增强书稿化能力。`

## 2. 总体策略

整个系统应按三阶段推进：

1. `Phase 1：跑通核心闭环`
2. `Phase 2：增强语义调度与知识整理`
3. `Phase 3：走向书稿化与成熟产品形态`

核心原因是：

1. 如果 Phase 1 的闭环没有跑通，后面的智能规划和复杂结构都没有基础
2. 如果过早做复杂图谱、复杂 agent 或复杂整理机制，系统会迅速失控
3. 用户真正最早需要的不是“高级能力很多”，而是“这个东西已经能用，而且越用越有积累”

## 3. Phase 1：跑通核心闭环

### 3.1 阶段目标

Phase 1 的目标只有一个：

`验证系统能否通过对话持续积累数学知识，并且让后续问题真的复用前面积累的内容。`

这是一切后续阶段的基础。

### 3.2 必须交付的核心能力

Phase 1 必须做的能力如下：

1. `对话主入口`
   用户能够直接提问、继续追问，不需要先操作复杂结构。

2. `已有知识引用回答`
   系统能够判断当前问题是否可由已有知识回答，并通过 `summary + detail + hyperlink` 的方式组织回答。

3. `知识不足时的待沉淀分流`
   系统能够识别知识缺口，先形成一组 `Pending Draft`，而不是直接无边界扩写。

4. `基础知识沉淀`
   回答中产生的高价值内容可以转成 `Knowledge Node`，并在后续被引用。

5. `基础 Fork`
   用户可以从某个回答片段或引用继续深入，新分支继承语义起点，而不是继承全部历史消息。

6. `基础 Symbol Registry`
   系统能够维持主要符号约定，避免明显冲突和漂移。

7. `基础 /compact`
   系统能够压缩非活跃内容、生成 summary 视图、合并明显重复的小片段。

8. `基础三域界面`
   至少具备：
   - 主对话区
   - 知识树/大纲区
   - 引用详情区

### 3.3 本阶段明确不做的事

Phase 1 不应做：

1. 不做复杂 DAG 可视化
2. 不做复杂多代理自治
3. 不做精细分支合并机制
4. 不做复杂版本管理系统
5. 不做高级书稿导出能力
6. 不做复杂知识桥接自动生成
7. 不做形式化验证集成

### 3.4 产品重点

Phase 1 的重点不是“功能多”，而是“闭环稳”。需要重点看四件事：

1. 用户问一个问题后，系统是否真的先判断已有知识
2. 当知识不足时，新增内容是否受控
3. 多轮对话后，知识是否真的在累积并被复用
4. fork 和 compact 是否已经能抑制上下文膨胀

### 3.5 验收标准

Phase 1 完成的标志是：

1. 系统已经不是纯聊天机器人
2. 用户连续使用后，知识节点有稳定增长
3. 后续回答可以引用前面生成的知识节点
4. 用户能从局部内容继续 fork 深挖
5. `/compact` 后结构比原始对话更清楚
6. 符号不会在短周期内明显失控

### 3.6 为什么它必须先做

因为只有 Phase 1 跑通，才能证明这个产品最关键的价值成立：

`对话不是瞬时消耗，而是长期知识积累。`

## 4. Phase 2：增强语义调度与知识整理

### 4.1 阶段目标

Phase 2 的目标是：

`让系统从“能积累知识”提升到“能更聪明地调度知识、整理知识和引导知识生长”。`

如果说 Phase 1 是可用，那么 Phase 2 才开始体现这个系统真正的智能性。

### 4.2 必须增强的能力

Phase 2 应重点增强以下方向：

1. `更稳的上下文激活集规划`
   系统对当前问题的理解更精细，能够更好地区分：
   - 哪些节点只需要 summary
   - 哪些节点必须展开 detail
   - 哪些知识只应保持 latent 状态

2. `更强的意图识别`
   系统能够更清晰地区分用户当前是在：
   - 要定义
   - 要直觉解释
   - 要严格推导
   - 要例子
   - 要补前置知识
   - 要整理结构

3. `更智能的 Pending Draft 生成`
   系统能够更稳地判断本轮该补什么知识，而不是补太多或补太碎。

4. `更自然的 fork 建议`
   系统能在适当时机建议用户切出新分支，而不是等上下文已经失控后才处理。

5. `更强的 compact`
   `/compact` 不再只是做压缩，还能更明显地：
   - 合并重复节点
   - 统一符号
   - 回挂分支内容
   - 形成更稳定的汇总节点

6. `更稳的符号协调`
   符号表开始支持更清晰的作用域层次与局部例外。

7. `基础桥接能力`
   当两个已有节点之间缺少中间说明时，系统能更自然地生成桥接型知识节点。

### 4.3 本阶段不应越界的地方

Phase 2 仍应保持克制：

1. 不做完整知识图谱平台
2. 不做复杂自动重构到用户无法理解
3. 不做大规模后台预测式分支生成
4. 不做高度自治的复杂 agent 工作流

### 4.4 产品重点

Phase 2 的重点是把“会积累”升级为“会组织”。

需要重点观察：

1. 系统是否更少误拉无关上下文
2. 回答是否更贴近用户当前需要的表达层次
3. 知识库是否开始形成更清晰的主线和汇总结构
4. compact 后是否明显降低碎片化

### 4.5 验收标准

Phase 2 完成的标志是：

1. 多轮使用后，知识库不再只是堆积节点，而开始出现稳定层次
2. 系统对何时 fork、何时补前置、何时 compact 的判断更自然
3. 用户感受到系统不仅“记住了”，而且“会整理、会引导”
4. 数学内容的一致性明显优于 Phase 1

### 4.6 为什么它排在 Phase 2

因为这些能力都建立在 Phase 1 已经存在稳定知识资产的前提上。没有前面的知识积累，智能调度就没有对象可调度。

## 5. Phase 3：走向书稿化与成熟产品形态

### 5.1 阶段目标

Phase 3 的目标是：

`让系统从“对话中的知识积累器”演化为“可持续修订的数学书稿系统”。`

这一阶段，知识库不再只是支撑对话，而开始成为主资产。

### 5.2 重点建设方向

Phase 3 应重点推进：

1. `更成熟的书稿结构`
   知识树开始更明确地对应章节、小节和专题组织。

2. `更强的主线重排能力`
   系统能把探索时随机长出的内容，逐步回收为更适合阅读的章节结构。

3. `更丰富的跨主题桥接`
   系统开始支持更成熟的交叉引用和主题间桥接，但仍以树状主线为主。

4. `更强的导出与呈现能力`
   系统沉淀出的内容不只是内部节点，而是更接近可阅读、可编辑、可导出的书稿。

5. `更成熟的 Branch View`
   用户能更清楚地看到不同探索路径与主线的关系。

6. `更细致的知识状态管理`
   节点的草稿态、稳定态、整理态会更加清晰。

### 5.3 可以在这一阶段考虑的增强项

到了 Phase 3，才适合谨慎考虑以下方向：

1. 更明显的网络化关系展示
2. 更成熟的章节导出
3. 更细的结构整理策略
4. 更丰富的知识地图视图

这些方向都应建立在前两阶段已经稳定的基础上，而不是提前引入。

### 5.4 产品重点

Phase 3 的重点不是继续加“智能感”，而是把知识资产真正产品化。

需要重点观察：

1. 用户是否开始把系统当作长期书稿工作台
2. compact 后的结果是否越来越接近真正可读的小节或章节
3. 对话和知识库之间是否形成健康分工：
   - 对话负责探索、修订、解释
   - 知识库负责稳定内容与长期结构

### 5.5 验收标准

Phase 3 完成的标志是：

1. 用户已经能长期使用系统沉淀一门数学主题
2. 沉淀结果具备明显书稿结构，而不是一堆问答碎片
3. 分支探索与主线书稿可以共存，而不相互破坏
4. 系统开始从“知识助手”升级为“书稿构建工具”

## 6. 三阶段的依赖关系

三阶段之间是严格递进关系。

### 6.1 Phase 1 -> Phase 2

Phase 1 提供：

1. 基础知识资产
2. 基础引用关系
3. 基础分支能力
4. 基础符号约束

Phase 2 在此基础上增强：

1. 激活集调度
2. 语义规划
3. 知识整理质量
4. 结构稳定性

### 6.2 Phase 2 -> Phase 3

Phase 2 提供：

1. 更干净的知识层次
2. 更好的 compact 结果
3. 更可靠的符号一致性
4. 更自然的知识主线

Phase 3 才能进一步做：

1. 章节化
2. 书稿化
3. 更成熟的呈现和导出

## 7. 第一版产品的清晰边界

如果现在要定义“第一版产品”，应当明确：

`第一版产品 = Phase 1 完整跑通，不以 Phase 2 和 Phase 3 的能力为上线前提。`

也就是说，第一版不需要证明系统已经很聪明，只需要证明：

1. 它能通过对话积累知识
2. 它能引用已有知识回答
3. 它能在缺口处受控扩展
4. 它能通过 fork 管理深入探索
5. 它能通过 compact 保持长期可用

这才是最正确的第一版产品边界。

## 8. 推荐的实际推进顺序

如果按真正落地顺序排，建议这样理解：

### 8.1 先做最小闭环

先确保以下动作已经连起来：

1. 用户提问
2. 系统判断已有知识是否足够
3. 足够则引用回答
4. 不足则生成待沉淀条目
5. 新内容沉淀成知识节点
6. 后续问题能复用这些节点

这一步如果没跑通，不要继续扩功能。

### 8.2 再做分支与整理

当最小闭环可用后，再增强：

1. fork 的局部深入体验
2. compact 的整理能力
3. 基础符号一致性

这是让系统可以长期使用的关键。

### 8.3 最后做更强智能与书稿化

当系统已经具备“长期使用不会越用越乱”的特征后，再增强：

1. 更强的语义规划
2. 更稳的结构整理
3. 更成熟的章节主线
4. 更好的书稿输出

## 9. 最终结论

这套系统的实施顺序必须服从一个原则：

`先证明知识能积累，再证明知识会整理，最后证明知识能成书。`

因此最合理的阶段划分是：

1. `Phase 1：跑通核心闭环`
2. `Phase 2：增强语义调度与知识整理`
3. `Phase 3：走向书稿化与成熟产品形态`

如果后续继续往前推进，这份文档之后最自然的下一层文档就是：

`将 Phase 1 再拆成更细的里程碑，例如 Milestone A / B / C，明确第一版产品的实际实施顺序。`
