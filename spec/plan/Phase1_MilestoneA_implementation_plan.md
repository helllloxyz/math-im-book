# Milestone A Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 跑通第一版最关键的知识闭环，让系统能够把问答过程转化为可复用知识，并在后续问答中再次利用这些知识。

**Architecture:** 以 `Chat Session + Knowledge Node + Pending Draft + Reference` 为最小骨架，先建立“复用已有知识 / 扩展缺失知识”双分流，再让新增内容沉淀回知识节点。界面只提供最小可见性，不抢在闭环之前做复杂交互。
在实现结构上，agent 应参考 skill 的设计逻辑：主入口稳定、规划输出统一 action、具体能力按 rule/skill 插拔扩展。

**Tech Stack:** 待定；本计划暂不绑定具体前后端框架、数据库或模型供应商。

---

## 1. 实施范围

本计划只覆盖 `Milestone A：问答与知识节点闭环`，不覆盖：

1. 复杂 fork
2. 复杂 compact
3. 复杂 symbol scope
4. 多代理自治
5. 复杂书稿导出

本计划的目标是把以下闭环做实：

1. 用户提问
2. 系统判断已有知识是否足够
3. 足够则引用回答
4. 不足则生成待沉淀条目
5. 新内容沉淀为知识节点
6. 后续问题可复用这些节点

## 2. 产出物

完成本计划后，系统应至少拥有以下产出：

1. 一套最小知识节点定义
2. 一套“复用 / 扩展”双分流规则
3. 一套最小 `Agent Action` 协议
4. 一种统一的引用式回答结构
5. 一种受控的待沉淀条目机制
6. 一种把新增内容沉淀为正式知识节点的流程
7. 一种最小的知识可见性界面或视图

## 3. 验收总标准

整个 Milestone A 完成时，必须同时满足：

1. 系统不会对所有问题都用同一种回答模式
2. 已有知识足够时，回答能明确复用已有节点
3. 已有知识不足时，系统会先形成待沉淀条目
4. 分流结果能稳定落到统一的 `Agent Action`
5. 新增知识能够进入知识库
6. 后续问题能够实际复用这些新增节点
7. 用户能看到系统中已有知识与当前新增知识

## 4. 实施顺序

### Task 1：冻结最小知识模型

**目标**

先把“什么是知识节点”定死，避免后面边做边改模型。

**必须完成的内容**

- [ ] 定义最小知识节点字段：`title`、`summary`、`detail`、`type`、`parent/source`
- [ ] 将第一版节点类型限制为两类：`原子节点`、`汇总节点`
- [ ] 明确 `summary` 是一级运行对象，而不是附属说明
- [ ] 仅保留最小关系集合：所属主题、来源会话/问题、被谁引用

**完成标志**

- [ ] 团队能用一句话定义“什么是第一版知识节点”
- [ ] 团队对第一版节点字段和节点类型没有分歧
- [ ] 不再新增与 Milestone A 无关的节点属性或关系

**依赖**

无。这是整个计划的起点。

### Task 2：建立问答双分流规则

**目标**

让系统面对问题时，先判断进入“复用模式”还是“扩展模式”。

**必须完成的内容**

- [ ] 定义“已有知识足够”的判断口径
- [ ] 定义“已有知识不足”的判断口径
- [ ] 明确系统只保留两种主模式：`复用模式`、`扩展模式`
- [ ] 明确不确定时的优先策略：优先进入受控扩展，而不是勉强复用

**完成标志**

- [ ] 团队能够明确列举出哪些情况进入复用模式
- [ ] 团队能够明确列举出哪些情况进入扩展模式
- [ ] 产品层不存在第三种模糊主路径

**依赖**

- [ ] Task 1 已完成

### Task 3：冻结 Agent Action 协议

**目标**

把 agent 的规划输出从“隐式逻辑”提升为稳定 contract，便于后续按 skill/rule 方式扩展。

**必须完成的内容**

- [ ] 定义最小 `Agent Action` 结构
- [ ] 明确本阶段至少支持的 action：`reuse_answer`、`expand_with_drafts`
- [ ] 明确 action 中必须包含：`action_type`、`selected_node_ids`、`draft_requests`、`user_visible_reason`
- [ ] 明确后续新增能力优先通过新增 action 或 rule 扩展，而不是重写主流程

**完成标志**

- [ ] 团队能清楚描述“planner 输出什么，执行器消费什么”
- [ ] `复用模式` 与 `扩展模式` 都已经能映射到统一 action
- [ ] 后续新增能力已有明确扩展位，而不是只能塞进主控制流

**依赖**

- [ ] Task 1 已完成
- [ ] Task 2 已完成

### Task 4：建立引用式回答规范

**目标**

当系统进入复用模式时，回答必须体现“这是在使用已有知识”，但仍保持自然可读。

**必须完成的内容**

- [ ] 固定回答骨架为 `summary + detail + hyperlink`
- [ ] 明确回答先是自然讲解，再由引用支撑
- [ ] 明确 `detail` 只做局部展开，不允许整节点全文默认注入
- [ ] 明确引用来源对用户可见，并能查看对应节点

**完成标志**

- [ ] 用户可以感知当前回答是建立在已有节点上的
- [ ] 回答不会因为强调引用而退化成知识片段拼接
- [ ] 团队对“什么时候只用 summary，什么时候展开 detail”有统一理解

**依赖**

- [ ] Task 1 已完成
- [ ] Task 2 已完成
- [ ] Task 3 已完成

### Task 5：建立待沉淀条目机制

**目标**

当系统进入扩展模式时，先把缺口显式化，而不是直接无限扩写。

**必须完成的内容**

- [ ] 将待沉淀条目限制为三类：`缺失定义`、`缺失桥接`、`缺失展开`
- [ ] 明确待沉淀条目不是正式知识节点
- [ ] 定义待沉淀条目的粒度原则：只补当前回答真正需要的缺口
- [ ] 明确待沉淀条目与当前回答的关系解释方式

**完成标志**

- [ ] 系统在知识不足时，能够先明确缺什么
- [ ] 待沉淀条目数量和粒度受控，不会一轮扩出一个大纲
- [ ] 用户可以理解“为什么这次要补这些知识”

**依赖**

- [ ] Task 1 已完成
- [ ] Task 2 已完成
- [ ] Task 3 已完成

### Task 6：建立基础知识沉淀流程

**目标**

让新增内容真正进入知识库，并参与后续复用。

**必须完成的内容**

- [ ] 明确哪些新增内容值得沉淀
- [ ] 明确沉淀后节点如何归属到主题或父级结构
- [ ] 明确沉淀节点必须满足的最小质量要求：标题、summary、detail
- [ ] 明确沉淀后的节点可在后续问题中再次被引用

**完成标志**

- [ ] 新增知识不再只停留在聊天记录里
- [ ] 新增节点能够进入知识树或知识列表
- [ ] 后续问题中能够实际复用这些新节点

**依赖**

- [ ] Task 1 已完成
- [ ] Task 2 已完成
- [ ] Task 3 已完成
- [ ] Task 4 已完成
- [ ] Task 5 已完成

### Task 7：建立最小知识可见性

**目标**

让用户看见系统中已有知识、当前引用和本轮新增内容。

**必须完成的内容**

- [ ] 展示当前已有知识节点列表或最小树状大纲
- [ ] 展示当前回答引用了哪些知识节点
- [ ] 展示当前新增了哪些待沉淀条目或正式节点
- [ ] 明确可见性服务于知识闭环，而不是转向复杂知识管理平台

**完成标志**

- [ ] 用户能看到系统中已经积累了什么
- [ ] 用户能看到当前回答与哪些节点相关
- [ ] 用户能看到本轮新增知识处于候选态还是正式态

**依赖**

- [ ] Task 3 已完成
- [ ] Task 4 已完成
- [ ] Task 5 已完成
- [ ] Task 6 已完成

## 5. 推荐执行节奏

建议按以下节奏推进，不要并行启动过多方向：

### 第一步：先做对象和分流

- [ ] 完成 Task 1
- [ ] 完成 Task 2
- [ ] 完成 Task 3

这是系统从“普通聊天”变成“知识型问答”的前提。

### 第二步：再做回答与扩展规范

- [ ] 完成 Task 4
- [ ] 完成 Task 5

这是系统形成“复用已有知识 / 受控补足知识”双路径的关键。

### 第三步：最后打通知识闭环

- [ ] 完成 Task 6
- [ ] 完成 Task 7

这是系统从“知道该怎么做”变成“真的开始积累知识”的关键。

## 6. 关键风险与控制

### 风险 1：过早把知识模型做重

表现：

1. 节点类型太多
2. 关系类型太多
3. 一开始就想建复杂知识图谱

控制方式：

- [ ] 严格限制第一版只保留最小节点模型

### 风险 2：系统仍然退化成普通聊天

表现：

1. 没有真正的复用模式
2. 所有问题都直接回答
3. 已有节点对回答没有真实影响

控制方式：

- [ ] 优先完成 Task 2、Task 3 和 Task 4，再推进其他能力

### 风险 3：agent 能力被写死在主流程里

表现：

1. 每增加一个能力都要改主分流逻辑
2. 后续加 fork、compact、symbol align 时会不断返工
3. planner 与执行器职责混乱

控制方式：

- [ ] 先冻结 `Agent Action` 协议，再实现回答、draft、沉淀

### 风险 4：扩展模式失控

表现：

1. 一次补太多知识
2. 待沉淀条目粒度过碎
3. 回答顺带生成大量未来不一定需要的内容

控制方式：

- [ ] 将待沉淀条目限制在“当前回答所需最小缺口”

### 风险 5：沉淀动作等于保存聊天记录

表现：

1. 沉淀节点没有 summary
2. 沉淀节点缺少结构归属
3. 后续问题无法真正复用沉淀内容

控制方式：

- [ ] 把 Task 5 的“可复用性”作为硬验收标准

### 风险 6：前端先行，闭环未成

表现：

1. 先做复杂侧栏和结构展示
2. 但知识沉淀和复用机制还没跑通

控制方式：

- [ ] 将 Task 6 明确放在 Task 5 之后

## 7. 里程碑验收流程

建议按以下方式验收 Milestone A：

### 场景一：已有知识复用

- [ ] 先准备一批基础知识节点
- [ ] 提一个可由现有知识回答的问题
- [ ] 验证系统是否引用已有节点回答
- [ ] 验证回答中的引用是否可见

### 场景二：知识不足扩展

- [ ] 提一个现有知识不足的问题
- [ ] 验证系统是否先形成待沉淀条目
- [ ] 验证新增内容是否围绕这些条目展开
- [ ] 验证新增内容是否最终沉淀为节点

### 场景三：跨轮次复用

- [ ] 在前一轮新增知识后，发起后续相关问题
- [ ] 验证系统是否能复用刚刚沉淀的新节点
- [ ] 验证用户能够看见知识在持续积累

只有三个场景都成立，Milestone A 才算真正成立。

## 8. 阶段完成后的状态

完成本计划后，系统应处于这样一种状态：

1. 已经具备最小知识模型
2. 已经具备复用 / 扩展双模式
3. 已经具备引用式回答
4. 已经具备待沉淀条目
5. 已经具备基础知识沉淀
6. 已经具备最小知识可见性

这意味着系统已经不再是“会回答问题”，而是：

`开始通过问答持续构建知识。`
