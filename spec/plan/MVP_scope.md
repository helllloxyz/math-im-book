# 数学知识演化系统 MVP 范围文档

## 1. 文档目标

本文档基于 [`System_design.md`](./System_design.md)，收束第一阶段必须实现的产品范围。

目标不是定义终局系统，而是明确：

1. 第一阶段要验证什么
2. 哪些能力必须有
3. 哪些能力明确不做或后置
4. MVP 成功的判断标准是什么

本文档继续停留在产品与系统边界层，不展开实现细节。

## 2. MVP 的核心判断

这个系统的第一阶段不应追求“自动写书”，而应验证下面这件事是否成立：

`用户可以通过对话逐步构建数学知识库，系统能够复用已有知识、在知识缺失时产生受控新增内容，并通过分支、引用、符号表和 compact 维持长期可用性。`

如果这件事能成立，后续再扩展成更成熟的书稿系统才有意义。

## 3. MVP 的目标

MVP 只验证六个核心能力：

1. `对话驱动`
   用户通过自然提问驱动系统，而不是先操作复杂知识结构。

2. `知识复用`
   系统能判断已有知识是否足够，并通过引用已有节点回答问题。

3. `受控扩展`
   当知识不足时，系统不会无边界生成，而是先形成一组待沉淀条目。

4. `分支探索`
   用户可以围绕某个片段或引用继续深入，而不污染整个上下文。

5. `符号一致`
   数学符号、定义和命名不会在长期对话中快速漂移。

6. `整理收束`
   系统能够通过 `/compact` 将探索态内容逐步整理为更稳定的知识结构。

## 4. MVP 的非目标

以下能力在第一阶段明确不做，或只保留极弱形式：

1. 不做完整 DAG 图谱系统
2. 不做复杂版本管理和知识 diff 系统
3. 不做高度自治、多代理自演化系统
4. 不做形式化证明集成
5. 不做复杂的计算沙盒与自动验证平台
6. 不做大规模预测式后台预生成
7. 不做过强的自动重构，避免系统过度智能化导致不可控

MVP 重点是验证“对话驱动的知识演化”这个主机制，而不是把所有远期能力塞进第一版。

## 5. MVP 用户画像

第一阶段主要面向以下用户：

1. 自己在长期学习或写作数学内容的人
2. 希望一边问、一边整理、一边沉淀知识的人
3. 不满足于纯聊天机器人，希望结果最终能沉淀成结构化文本的人

MVP 暂不优先面向：

1. 需要强协作的多人编辑团队
2. 需要严格形式化证明验证的研究型场景
3. 需要复杂知识图谱可视分析的平台型使用者

## 6. MVP 的最小对象集

MVP 中只保留最小但完整的一组核心对象。

### 6.1 Chat Session

负责承载用户问题、当前对话状态与当前激活上下文。

### 6.2 Knowledge Node

负责承载可复用的长期知识内容。

MVP 中允许两类节点：

1. `原子节点`
2. `汇总节点`

不再继续细分过多子类型，以免第一阶段建模过重。

### 6.3 Symbol Registry

负责维护基础符号一致性。

MVP 中只要求：

1. 能记录当前重要符号
2. 能在回答时注入约束
3. 能发现基础冲突

### 6.4 Pending Draft

负责表达本轮问题中需要新增但尚未沉淀的知识条目。

### 6.5 Reference

负责表达回答与知识节点之间的可追溯引用。

### 6.6 Fork

负责表达从当前会话或某个引用点切出的新探索分支。

## 7. MVP 必须具备的能力

### 7.1 已有知识回答

当用户提出问题时，系统必须能：

1. 识别相关已有知识
2. 以 `summary + detail + hyperlink` 的方式组织回答
3. 让用户知道当前回答复用了哪些知识节点

这是 MVP 最核心的验证点之一。

### 7.2 缺失知识分流

当已有知识不足时，系统必须能：

1. 判断“当前知识不够”
2. 先形成一组待沉淀条目
3. 说明当前回答依赖了哪些新增知识
4. 将新增内容与正式知识节点区分开

这一步的重点不是生成很多内容，而是让新增知识有边界、有归属。

### 7.3 基础知识沉淀

MVP 必须允许系统把有价值的回答结果沉淀为知识节点。

沉淀至少要做到：

1. 有标题或主题归属
2. 有 summary
3. 有 detail
4. 可被未来引用
5. 与当前会话或父级主题建立关系

### 7.4 基础分支能力

MVP 必须支持最基础的 fork：

1. 基于回答中的某个引用继续深入
2. 基于用户选中的片段继续追问
3. 在新分支中维持较干净的局部上下文

这里先不要求复杂的分支合并机制，只要求分叉可用、语义清晰。

### 7.5 基础上下文管理

MVP 不需要复杂上下文编排器，但必须具备基础激活机制：

1. 当前会话目标可见
2. 当前回答引用的知识集合可识别
3. 非当前焦点内容不会被全量塞入上下文
4. 远处知识至少可降为 summary

### 7.6 基础符号一致机制

MVP 必须对数学场景做最低限度保护：

1. 系统知道当前重要符号约定
2. 回答时优先复用已有符号
3. 新内容和旧符号冲突时能够提示或改写

### 7.7 基础 compact

MVP 中 `/compact` 不要求完整重构能力，但至少要做到：

1. 压缩非活跃分支
2. 合并明显重复的小片段
3. 对近期新增内容做基础符号对齐
4. 生成更适合长期保留的 summary 视图

## 8. MVP 的用户交互范围

### 8.1 默认交互方式

MVP 以自然对话为主入口。

用户可以：

1. 直接提问
2. 继续追问
3. 选中内容继续问
4. 点开引用节点查看详情

### 8.2 最小命令集

MVP 建议只保留少量高价值命令：

1. `/compact`
2. `/fork`
3. `/outline`
4. `/symbols`

不建议第一阶段就放入过多命令，否则会把产品重心拉向“命令系统”而不是“知识构建”。

### 8.3 MVP 界面结构

MVP 前端只需满足最基本的三域结构：

1. 主对话区
2. 知识树或大纲侧栏
3. 引用详情或节点预览侧栏

第一阶段不需要复杂可视化，只要让“当前在聊什么、引用了什么、知识沉淀到哪里了”这三件事可见即可。

## 9. MVP 的 LLM 与 Agent 角色

MVP 中，LLM 的核心价值不在于“多会写”，而在于：

1. 理解用户问题的真实意图
2. 判断已有知识是否足够
3. 识别本轮知识缺口
4. 规划当前最小相关知识集合
5. 组织自然回答
6. 在 compact 时参与语义归并和摘要重写

MVP 中不要求复杂 agent 编排，但必须已经体现出一种受约束的规划能力：

1. 知道何时复用
2. 知道何时扩展
3. 知道何时建议 fork
4. 知道何时建议 compact

## 10. MVP 成功标准

MVP 是否成立，不看生成了多少内容，而看以下判断是否成立：

### 10.1 单轮层面

1. 用户问题能被归类为“复用已有知识”或“需要新增知识”
2. 回答中存在明确引用来源
3. 当知识不足时，新增内容边界明确，而不是随意扩写

### 10.2 多轮层面

1. 连续对话后，知识节点确实在累积
2. 后续问题能复用前面沉淀的内容
3. 分支探索不会快速污染主线
4. 符号不会明显漂移失控

### 10.3 长周期层面

1. 系统通过 compact 后，知识结构比原始对话更清晰
2. 沉淀出的内容开始具备“书稿”的雏形
3. 用户感受到自己是在“构建一本会生长的数学书”，而不是“反复和机器人闲聊”

## 11. MVP 之后的自然演进方向

如果 MVP 验证成功，后续演进顺序建议如下：

1. 强化上下文激活与 agent 规划
2. 强化知识节点的桥接、汇总和重排能力
3. 强化分支间回挂与主线整理
4. 强化导出、章节化和书稿生成能力
5. 最后再考虑更复杂的知识网络化表达

## 12. 最终结论

MVP 第一阶段不是要做一个“大而全”的数学知识平台，而是要做成一个：

`能通过对话持续积累数学知识、可复用、可分支、可整理、符号基本一致的最小系统。`

只要第一阶段把以下闭环跑通，就已经成功：

1. 用户提问
2. 系统判断已有知识是否足够
3. 足够则引用回答
4. 不足则产生待沉淀条目并受控扩展
5. 内容沉淀为知识节点
6. 用户可基于片段或引用继续 fork
7. 系统通过 compact 持续整理结构

这个闭环一旦成立，完整系统设计中的其他高级能力都可以在后续版本中自然生长出来。
