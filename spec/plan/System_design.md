# 数学知识演化系统设计文档

## 1. 文档目标

本文档从 [`User_init_dialog.md`](./User_init_dialog.md) 的初始需求出发，结合 [`AI_top_down.md`](./AI_top_down.md)、[`AI_symbol.md`](./AI_symbol.md)、[`AI_agent.md`](./AI_agent.md)、[`AI_opt.md`](./AI_opt.md) 中有价值的建议，收束为一份完整系统设计。

本文档关注：

1. 系统定位
2. 核心对象与关系
3. 用户交互模型
4. 知识沉淀与上下文机制
5. 数学场景下的符号一致性
6. 长期演化过程中的整理与边界控制

本文档暂不展开：

1. 具体实现技术栈
2. 数据库存储细节
3. 模型选型与推理流程实现
4. API 设计与工程拆分

## 2. 初始需求总结

从初始需求中可以提炼出以下核心诉求：

1. 现有“自上而下生成整本书”的逻辑需要改变。
2. 仍然保留宏观上的自上而下主线，但内容不应一次生成，而应在与用户交互过程中逐渐生成。
3. 知识结构更适合像一棵树一样不断分叉，而不是线性展开。
4. 在生成过程中必须维护 context，避免无关内容长期占据上下文。
5. 希望借鉴 `skill markdown` 的思路，用 markdown 作为知识载体，支持按需加载、卸载、压缩。
6. 数学内容必须重视定义、符号和标记的一致性。
7. 系统不能过于复杂，否则会失去灵活性与智能性。
8. 需要类似 `/compact` 的整理能力，用来自动收束内容、统一符号、压缩上下文。
9. 前端交互需要同时适配“网络状知识文本”和“命令行式交互逻辑”。
10. 新的总体方向是：以对话为基础，引入 agent 思路，维护 context = state + memory。

据此，系统本质上不是“自动写书工具”，而是一个：

`以对话驱动、以知识节点沉淀、可分叉演化、面向数学书稿长期构建的知识系统。`

## 3. 建议文档采纳结果

### 3.1 采纳的方向

从 AI 建议中，以下方向被采纳并吸收为正式设计的一部分：

1. `Markdown + 元数据头` 作为知识节点的主要承载形式
2. `summary + detail + hyperlink` 的引用机制
3. `Chat` 与 `Knowledge Base` 双核心并列
4. `Fork` 作为隔离上下文和分叉探索的核心机制
5. `Symbol Registry` 作为数学一致性的一级对象
6. `/compact` 作为知识整理与重构机制，而不是单纯压缩命令
7. `树状展示为主，交叉引用为辅` 的知识组织方式
8. `LLM 负责语义理解、路由、编排、规划`，而不是只做文本生成
9. `待沉淀条目` 机制，用于在缺失知识时先定义增长边界

### 3.2 暂不采纳或后置的方向

以下建议有价值，但不适合作为当前完整系统设计的核心能力，暂时后置：

1. 完整 DAG 可视化与强图谱化建模
2. 语义版本控制和节点级复杂版本演化机制
3. 概率性预取和大规模后台分支预热
4. Lean/Isabelle 等形式化证明集成
5. 复杂交互沙盒、自动计算验证平台
6. 过早引入重型工作流引擎或高度自治 agent 系统

后置原因很明确：

1. 当前目标是“强大而简单”
2. 优先保证对话驱动、知识沉淀、符号一致、分支管理和整理机制
3. 避免系统在早期因为过重设计而失去可用性

## 4. 系统定位

### 4.1 系统定义

本系统定义为：

`一个以对话为入口、以知识节点为长期记忆、以 LLM 语义理解和 agent 规划为驱动、面向数学书稿持续演化的知识构建系统。`

### 4.2 核心目标

1. 让用户以自然对话方式探索数学内容
2. 让对话结果逐步沉淀为可复用的知识库，而不是堆积成聊天记录
3. 让知识库最终具备书稿化组织能力
4. 让长期生成过程中保持符号、定义、依赖关系的一致性
5. 让系统能够支持分叉探索，同时控制上下文膨胀
6. 让知识增长始终可整理、可追溯、可重构

### 4.3 核心原则

1. `Chat` 与 `Knowledge Base` 双核心，并列存在
2. `回答属于 Chat，事实属于 Knowledge`
3. 默认不做全文加载，而采用 `summary -> detail -> hyperlink`
4. 知识粒度采用混合模式，但关键知识必须支持原子化
5. LLM 负责理解和规划，系统结构负责约束和沉淀
6. 优先简单、可持续演化，不追求一开始就做成复杂知识图谱平台

## 5. 核心对象模型

### 5.1 Chat Session

`Chat Session` 是一次对话主线或某个分支上的探索单元，不只是消息列表，而是一个语义工作流容器。

它承载：

1. 用户与系统的显式消息
2. 当前工作目标
3. 当前激活的知识上下文
4. 会话状态
5. 当前局部的语义规划

### 5.2 Knowledge Node

`Knowledge Node` 是长期知识的基本单元，用于承载可复用、可引用、可整理的知识内容。

节点可以表示：

1. 定义
2. 命题或定理
3. 推导片段
4. 例子
5. 小节说明
6. 汇总总结

### 5.3 Symbol Registry

`Symbol Registry` 是数学符号、记号和定义一致性的约束层。

它不是附属信息，而是系统的一等对象，用于：

1. 约束新内容生成
2. 检测符号冲突
3. 管理全局与局部作用域

### 5.4 Reference

`Reference` 用于表达：

1. 回答与知识节点之间的引用关系
2. 知识节点之间的依赖关系
3. 用户继续追问时的跳转入口

### 5.5 Pending Draft

`Pending Draft` 表示在当前问题下，系统识别出的“需要新增但尚未正式沉淀”的知识条目。

它的作用是：

1. 约束新增内容边界
2. 避免系统无边界扩写
3. 让知识增长过程可视、可管理

### 5.6 Fork

`Fork` 用于从当前会话或知识片段中切出新的探索分支。

它的目标不是复制所有历史，而是继承必要的语义起点，保持上下文纯净。

### 5.7 Agent Action

`Agent Action` 是 agent planning layer 的最小执行单元，用于把“理解后的决策”与“具体执行模块”解耦。

它的作用是：

1. 让规划层输出稳定协议，而不是直接耦合到具体实现
2. 让不同能力以 skill/rule 的形式插拔扩展
3. 让回答、待沉淀条目、整理、fork 等动作都共享统一入口

在完整系统中，典型 `Agent Action` 包括：

1. `reuse_answer`
2. `expand_with_drafts`
3. `ask_clarification`
4. `suggest_fork`
5. `compact_only`
6. `align_symbols`

## 6. 知识节点设计

### 6.1 知识粒度策略

系统采用混合粒度，但重要知识优先原子化。

具体分为两层：

1. `原子节点`
   用于承载稳定、可复用、需要严格一致性的内容，例如：
   - 数学定义
   - 符号约定
   - 命题和定理
   - 关键推导步骤
   - 核心例子

2. `汇总节点`
   用于承载更接近书稿阅读形态的小节内容，例如：
   - 主题讲解
   - 概念综述
   - 一段完整推导说明
   - 问题导向的总结

核心原则是：

1. `复用驱动原子化`
2. `阅读驱动汇总化`

### 6.2 节点的核心信息

每个知识节点至少应包含以下概念字段：

1. `ID`
2. `Title`
3. `Type`
4. `Summary`
5. `Detail`
6. `Relations`
7. `Symbol Scope`
8. `Status`

其中 `Summary` 是一级对象，不是附属说明，因为它是上下文装载与引用的主要输入。

### 6.3 条目拆分边界

一个知识点应拆成独立条目，当它满足以下任一条件时：

1. 会被多个地方重复引用
2. 需要单独维护符号一致性
3. 本身是明确的数学对象或结论
4. 可能成为未来 fork 的起点

否则优先留在汇总节点内部，不强拆。

## 7. 引用机制

### 7.1 三段式引用

系统默认采用 `summary + detail + hyperlink` 的引用方式。

1. `Summary`
   用于建立当前回答的上下文骨架
2. `Detail`
   在当前问题确实需要时按需局部展开
3. `Hyperlink`
   用于追溯来源、跳转原文、继续 fork

### 7.2 回答中的引用组织原则

当已有知识足以回答时，系统按照以下顺序组织内容：

1. 找到最相关的汇总节点
2. 补充必要的原子节点
3. 注入相关符号约束
4. 组织成自然回答
5. 在回答中保留可追溯引用

因此：

1. 叙述优先来自汇总节点
2. 精度优先来自原子节点
3. 一致性优先来自符号表

### 7.3 引用的产品目标

好的回答应该做到：

1. 阅读上自然连贯
2. 来源上可追溯
3. 深挖时可下钻
4. 不因复用旧知识而失去当前对话的连续性

## 8. 主流程设计

### 8.1 回答流程

系统处理一个用户问题时，主流程如下：

1. 用户提出问题
2. 系统理解当前意图和任务类型
3. 判断已有知识是否足以回答
4. 如果足够：
   - 拉取相关 summary
   - 按需展开 detail
   - 应用符号约束
   - 生成回答并附引用
5. 如果不足：
   - 生成一组 `Pending Draft`
   - 明确本轮所需新增知识边界
   - 基于新增候选内容回答当前问题
6. 回答结束后：
   - 将本轮有价值内容吸收到知识库
   - 更新引用关系
   - 必要时更新符号表和结构关系

### 8.2 Pending Draft 的作用

`Pending Draft` 主要解决三个问题：

1. 在知识缺失时限制生成边界
2. 将新增知识显式化，而不是埋入聊天记录
3. 让知识库增长是有组织的，而不是随机膨胀

它通常对应三类缺口：

1. 缺失定义
2. 缺失桥接
3. 缺失展开

## 9. Chat 与 Fork 模型

### 9.1 Chat 的本质

`Chat Session` 不只是消息流，而是一个语义工作流单元。

它至少包含四层：

1. 显式对话
2. 当前工作上下文
3. 会话状态
4. 隐式 agent 计划

### 9.2 Fork 的来源

`Fork` 可以由三种场景触发：

1. 从回答中的引用继续深入
2. 从当前问题的某个子目标切出单独分支
3. 从用户选中的片段开始继续追问

### 9.3 Fork 的继承原则

新分支不应继承全部消息历史，而应继承：

1. 必要的全局设定
2. 当前相关节点的摘要
3. 被选中的核心片段
4. 相关符号约束
5. 当前子任务目标

因此：

`Fork 继承的是语义起点，而不是完整消息历史。`

### 9.4 Fork 的价值

1. 控制上下文膨胀
2. 隔离不同探索路径
3. 支持多角度深入同一知识点
4. 使知识沉淀可以回挂到不同位置

## 10. 上下文管理

### 10.1 上下文的定义

上下文不应理解为“装多少文本”，而应理解为：

`当前会话中被激活的语义对象集合。`

### 10.2 上下文的四层结构

1. `Global Context`
   - 全局书稿目标
   - 全局符号表
   - 顶层知识地图
   - 用户长期偏好

2. `Session Context`
   - 当前会话目标
   - 当前路径上的核心节点
   - 当前回答依赖的摘要集合

3. `Focused Context`
   - 当前问题真正需要展开的 detail
   - 当前局部符号约束
   - 当前局部中间结论

4. `Latent Context`
   - 可能相关但暂不激活的节点摘要或索引

### 10.3 LLM 在上下文中的角色

LLM 在上下文管理中主要承担：

1. 识别当前问题意图
2. 判断问题属于哪种任务类型
3. 规划最小激活知识集合
4. 决定哪些节点只需 summary，哪些需要 detail
5. 判断是否需要新增 `Pending Draft`
6. 判断是否建议 fork 或 compact

因此，LLM 的主要价值不是单纯“生成文字”，而是：

1. 语义路由
2. 上下文编排
3. 任务规划
4. 表达层次选择

## 11. Agent Planning Layer

### 11.1 设计目标

为了保持灵活性，系统需要一个轻量的规划层，但不应演化为复杂的黑箱自治系统。

该层的作用是：在每轮对话中，做出受约束的智能决策。

### 11.2 每轮规划需要回答的问题

1. 当前问题是在使用已有知识，还是扩展知识库
2. 当前回答应偏总结、讲解、严格推导、例子说明还是补前置知识
3. 当前最小激活集应包含哪些节点
4. 当前是否存在符号或定义冲突风险
5. 回答后是应新增节点、更新节点，还是只补引用关系
6. 当前是否适合建议 fork 或 compact

### 11.3 规划层输出

规划层不应直接输出“最终回答文本”，而应优先输出一个稳定的 `Agent Action Contract`。

这个 contract 至少应包含：

1. `action_type`
2. `selected_node_ids`
3. `draft_requests`
4. `symbol_constraints`
5. `user_visible_reason`

这样做的意义是：

1. 回答器可以只负责回答生成
2. draft 生成器可以只负责知识缺口展开
3. fork 建议器可以只负责分支判断
4. 后续新增数学专用 skill 时，不需要改写整个主流程

### 11.4 规划层的定位

规划层不是替代用户做决定，而是提供一种稳定的智能：

1. 平时保持自然对话
2. 深入时自动切分任务
3. 长期使用时控制知识增长质量
4. 在系统复杂度增加时仍维持可理解性

### 11.5 Skill-Like 扩展原则

系统中的 agent 能力应尽量参考 skill 的设计逻辑：

1. 主入口稳定
2. 能力按规则或 skill 插拔
3. 新能力优先通过新增 action handler 或 rule 扩展
4. 尽量避免每次新增能力都改动主调度逻辑

这意味着系统后续新增如下能力时，都应优先作为独立 skill/action 接入：

1. 符号对齐
2. 桥接节点生成
3. 摘要压缩
4. 前置知识补足
5. 书稿重排

## 12. Symbol Registry

### 12.1 设计地位

数学场景下，符号一致性是系统正确性的基础之一，因此 `Symbol Registry` 必须是一等对象。

### 12.2 三个核心作用

1. `约束生成`
   在回答、扩展、整理之前注入相关符号约束
2. `冲突检测`
   检测新内容与旧约定的冲突
3. `作用域管理`
   支持全局与局部符号共存，但要求显式可追踪

### 12.3 作用域层次

符号表至少应区分：

1. 全局符号
2. 主题或章节级符号
3. 节点级局部符号
4. 当前会话临时符号

核心原则是：

`全局一致优先，局部例外允许，但必须显式声明。`

### 12.4 LLM 在符号协调中的价值

LLM 不只用于字符串替换，更用于理解：

1. 哪些符号在语义上冲突
2. 哪些只是不同记法
3. 哪种改写最不破坏阅读体验

## 13. /compact 的系统角色

### 13.1 定位

`/compact` 不是单纯的上下文压缩命令，而是系统的知识整理与重构机制。

它的本质是：

`把探索态内容重构为书稿态内容。`

### 13.2 主要职责

1. `上下文压缩`
   将非活跃分支从 detail 降级为 summary
2. `知识归并`
   合并过碎节点，减少知识碎片
3. `符号对齐`
   统一近期生成内容中的符号和定义表达
4. `结构重排`
   将对话中随机长出的内容回挂到更合理的书稿结构中

### 13.3 触发时机

`/compact` 可以由三种方式触发：

1. 用户显式触发
2. 系统在上下文过于臃肿时建议触发
3. 系统在长期积累后进行阶段性整理

### 13.4 整理原则

1. 优先建议式，而不是完全自动强制执行
2. 优先渐进式整理，而不是一次性大范围重写
3. 优先保留可追溯关系，而不是直接覆盖历史

### 13.5 LLM 在 compact 中的价值

LLM 适合参与：

1. 判断哪些节点语义重复
2. 判断哪些内容适合合并为汇总节点
3. 判断哪些分支适合压成摘要
4. 判断某些节点应回挂到哪条主线上
5. 将对话式材料重写成更适合书稿阅读的结构

## 14. 前端与交互模型

### 14.1 总体原则

前端不应做成复杂知识管理平台，也不应退化成纯聊天窗口。

建议采用：

`对话主导 + 知识辅助 + 分支可见`

的三域模型。

### 14.2 核心界面

1. `中间主对话区`
   用户的主要入口，负责提问、追问和当前回答
2. `左侧知识树/知识地图`
   展示书稿结构、主题层级、近期新增节点和待沉淀条目
3. `右侧引用预览/节点详情`
   展示当前引用节点的 summary、detail、符号依赖和继续 fork 的入口

### 14.3 三种主要视图

1. `Chat View`
2. `Knowledge View`
3. `Branch View`

展示上以树状层级为主，不以复杂 DAG 可视化作为默认入口。

### 14.4 用户操作类型

用户操作应分为四类：

1. `自然对话操作`
   - 直接提问
   - 继续追问
   - 切换解释层次
   - 比较不同概念或路径

2. `基于内容的局部操作`
   - 选中片段继续问
   - 基于引用继续展开
   - 请求更多 detail
   - 请求拆分或汇总节点

3. `知识管理操作`
   - 查看知识树
   - 查看待沉淀条目
   - 接受、修改或忽略候选条目
   - 查看引用关系
   - 查看符号表

4. `系统整理操作`
   - `/compact`
   - `/fork`
   - `/back`
   - `/focus`
   - `/symbols`
   - `/outline`

### 14.5 交互层原则

1. 自然对话是默认入口
2. 命令式操作是增强层
3. 高阶用户可以精细控制系统
4. 普通用户不必理解内部结构也能使用

## 15. 回答的产品形态

系统回答应同时满足自然性和知识可追溯性。

理想回答包含：

1. `主回答`
   面向当前问题，保持自然、连贯、可读
2. `引用支撑`
   关键结论能挂到知识节点
3. `可继续动作`
   提供自然的下步选择，例如深入、补前置、沉淀节点或 fork
4. `系统动作透明度`
   在必要时说明引用了哪些知识、发现了哪些缺口、新增了哪些候选条目

## 16. 系统生命周期

### 16.1 探索期

特点：

1. 用户频繁提问
2. 分支增长较快
3. 候选条目较多
4. 结构尚不稳定

系统重点：

1. 快速理解意图
2. 控制新增知识边界
3. 用 fork 隔离探索路径

### 16.2 积累期

特点：

1. 开始形成稳定主题
2. 常见概念已有沉淀
3. 汇总节点逐渐增多
4. 符号表趋于稳定

系统重点：

1. 提高知识复用率
2. 强化引用机制
3. 补桥接节点
4. 增加 compact 频率

### 16.3 整理期

特点：

1. 知识碎片需要归并
2. 多分支内容需要回挂主线
3. 书稿结构开始显现

系统重点：

1. 触发更强的 compact
2. 重排知识结构
3. 统一符号与术语

### 16.4 书稿期

特点：

1. 系统更像一本可修订的书
2. 对话更多承担修订、补充、局部重写功能

系统重点：

1. 让知识库成为主资产
2. 让 chat 成为编辑与解释入口
3. 控制分叉对稳定结构的扰动

## 18. 边界控制

为了保持“强大而简单”，系统需要明确边界。

### 18.1 不追求一次性自动写完整本书

系统应通过长期对话逐步生长，而不是一次生成整本内容。

### 18.2 不让知识库退化为聊天归档

聊天记录不是知识库。只有经过判断、整理和引用化的内容才进入长期层。

### 18.3 不让知识节点过度原子化

原子化只服务复用、一致性和未来展开，不为结构而结构。

### 18.4 不让 agent 完全黑箱决策

关键动作应尽量透明，例如：

1. 使用了哪些知识
2. 新增了哪些条目
3. 进行了哪些整理
4. 为什么建议 fork 或 compact

### 18.5 不把前端做成复杂图谱平台

用户首先是在讨论数学，其次才是在管理知识。

### 18.6 不让 /compact 成为破坏性自动重写

compact 应以建议式、渐进式、可追溯为原则，而不是不可逆的大改写。

## 19. 最终结论

本系统的核心不是“更会聊天”，而是：

1. 能判断已有知识是否足以支撑当前回答
2. 在知识缺口处先生成合适的待沉淀条目
3. 通过 `summary + detail + hyperlink` 保持回答连贯且可复用
4. 通过 `fork` 管理探索分支
5. 通过 `Symbol Registry` 维持数学一致性
6. 通过 `/compact` 将探索态内容整理为书稿态结构
7. 通过 LLM 的语义理解和 agent 规划能力，使整个系统保持灵活、智能而不失控

最终，这个系统应当成为：

`一个会随着对话不断生长、整理、收束，最终演化成数学书稿的知识构建工具。`
