# Milestone A 产品任务顺序

## 1. 文档目标

本文档基于 [`Phase1_milestones.md`](./Phase1_milestones.md)，继续将 `Milestone A：问答与知识节点闭环` 拆解为更具体的产品任务顺序。

这里关注的不是代码开发步骤，而是：

1. 第一版最早应该先完成哪些产品能力
2. 这些能力之间的先后依赖是什么
3. 哪一步完成后，才能安全推进下一步
4. 如何避免在第一阶段同时做太多事而失焦

## 2. Milestone A 的唯一核心

Milestone A 的本质不是“做一个聊天页面”，也不是“先做一个知识库界面”，而是先证明：

`系统已经能够把问答过程转化为可复用知识，并在后续问答中再次利用这些知识。`

因此所有任务顺序都应服从这一目标。

## 3. 总体推进原则

Milestone A 的推进顺序应遵循：

1. `先建立知识节点最小模型`
2. `再建立问答时的知识判断`
3. `再建立引用式回答`
4. `再建立待沉淀条目`
5. `最后建立最小知识可见性`

也就是说，先让系统内部闭环成立，再把它逐步暴露给用户。

## 4. Task A1：定义最小知识节点

### 4.1 目标

先定义系统中“什么叫一个可复用知识节点”。

因为如果知识节点本身不清楚，后面的引用、沉淀、待扩展都会没有边界。

### 4.2 本任务要确定的内容

一个最小知识节点至少应具备：

1. `标题或主题名`
2. `summary`
3. `detail`
4. `基础类型`
   这里只需要区分：
   - 原子节点
   - 汇总节点
5. `与其他节点的最小关系`
   至少包括：
   - 父级主题或来源
   - 被谁引用

### 4.3 为什么它必须最先做

因为后面所有能力都依赖它：

1. 没有节点，就无法判断“已有知识是否足够”
2. 没有节点，就无法生成可追溯引用
3. 没有节点，就无法把新内容沉淀下来

### 4.4 完成标志

当团队能够明确回答“系统中的一个知识单元最少长什么样”，这个任务才算完成。

## 5. Task A2：建立已有知识判断能力

### 5.1 目标

系统面对一个问题时，先不急着回答，而是先判断：

`已有知识是否已经足够支撑当前问题。`

### 5.2 本任务要实现的产品行为

面对用户问题时，系统至少要能区分两类情况：

1. `已有知识足够`
2. `已有知识不足`

这里不要求判断绝对完美，但必须先有这个分流意识，否则系统会退化成普通聊天机器人。

### 5.3 为什么它排在第二个

因为 Milestone A 的核心闭环建立在“先判断、再行动”上。

没有这一步，就无法形成：

1. 复用已有知识
2. 缺口生成待沉淀条目

### 5.4 完成标志

当系统已经不再对所有问题都用同一种模式回答，而是开始出现“复用模式”和“扩展模式”的分流，这个任务才算完成。

## 6. Task A3：建立引用式回答

### 6.1 目标

当系统判断已有知识足够时，应通过引用而不是重新现编来回答。

### 6.2 本任务要形成的回答结构

回答至少应具备：

1. `自然叙述`
   用户看到的仍然是流畅回答，而不是数据库拼接文本。

2. `summary 级知识支撑`
   当前回答依托的是哪些已有知识节点。

3. `必要 detail`
   当问题需要时，展开局部细节。

4. `明确来源`
   用户能知道当前回答对应哪些知识节点。

### 6.3 为什么这一任务排在这里

因为只有先做完 A1 和 A2，系统才知道：

1. 有哪些节点可引用
2. 什么时候应该进入“引用回答模式”

### 6.4 完成标志

当用户能明确感受到“这次回答是在复用前面已有内容”，而不是系统重新说了一遍，这个任务才算完成。

## 7. Task A4：建立待沉淀条目

### 7.1 目标

当系统判断已有知识不足时，不能直接无限扩写，而要先明确缺什么。

### 7.2 本任务要形成的产品行为

面对知识缺口，系统至少要能形成：

1. `缺失定义`
2. `缺失桥接`
3. `缺失展开`

这三类中某一种或几种的待沉淀条目。

这些条目的作用是：

1. 限制新增内容边界
2. 让用户知道当前系统为什么需要扩展
3. 让新增内容未来有明确归属

### 7.3 为什么它不能更早做

因为如果没有前面的：

1. 节点模型
2. 已有知识判断
3. 引用式回答

那么系统根本不知道什么叫“缺失”，也就谈不上高质量的待沉淀条目。

### 7.4 完成标志

当系统在知识不足时，不再直接散漫生成，而是先明确“本轮需要补哪些知识点”，这个任务才算完成。

## 8. Task A5：建立基础知识沉淀

### 8.1 目标

让本轮新增内容真正进入知识库，而不是留在聊天记录里。

### 8.2 本任务要形成的产品行为

系统至少应支持：

1. 将本轮高价值新增内容转化为知识节点
2. 让新增节点与当前主题或已有节点建立关系
3. 让这些新节点能够在后续被再次引用

### 8.3 为什么它排在这里

因为只有当：

1. 缺口已经被显式化
2. 新内容边界已经清楚

沉淀动作才不会变成“把整段回答硬塞进知识库”。

### 8.4 完成标志

当新知识已经不再只是本轮回答的一部分，而是变成后续轮次真正可复用的知识资产，这个任务才算完成。

## 9. Task A6：建立最小知识可见性

### 9.1 目标

用户需要看到系统到底沉淀了什么，否则知识增长会变成黑箱。

### 9.2 本任务要形成的产品行为

至少要让用户看到：

1. 当前已有的知识节点列表或树状大纲
2. 当前回答引用了哪些节点
3. 当前新增了哪些候选或正式节点

### 9.3 为什么它放在最后

因为它依赖前面所有能力已经存在：

1. 有节点可展示
2. 有引用可展示
3. 有新增候选可展示

如果过早做界面展示，很容易变成展示空壳结构。

### 9.4 完成标志

当用户能够明显看到“系统里已经积累了什么”，并能理解当前回答和这些节点之间的关系，这个任务才算完成。

## 10. 推荐实施顺序

Milestone A 的推荐产品顺序应严格为：

1. `A1：定义最小知识节点`
2. `A2：建立已有知识判断能力`
3. `A3：建立引用式回答`
4. `A4：建立待沉淀条目`
5. `A5：建立基础知识沉淀`
6. `A6：建立最小知识可见性`

这个顺序不建议打乱。

## 11. 为什么这个顺序最合理

### 11.1 先定义“知识是什么”

否则后续所有动作都没有对象基础。

### 11.2 再定义“何时复用、何时扩展”

否则系统仍然会退化成统一模式问答。

### 11.3 再让回答具备知识感

否则用户无法感知系统和普通聊天工具的差异。

### 11.4 再让缺口显式化

否则系统会在知识不足时无边界扩写。

### 11.5 再让新增内容正式沉淀

否则新增内容仍然只是回答碎片。

### 11.6 最后再增强可见性

否则前端会先于产品闭环成型，容易本末倒置。

## 12. Milestone A 的完成判断

Milestone A 真正完成时，应同时满足：

1. 用户提问后，系统会先判断已有知识是否足够
2. 足够时，系统会通过引用已有节点回答
3. 不足时，系统会先形成待沉淀条目
4. 新内容能够沉淀为节点
5. 后续问题能复用这些节点
6. 用户能看到知识已经开始累积

只要这六件事已经成立，就说明：

`第一版最关键的知识闭环已经跑通。`

## 13. 当前最应该避免的误区

在 Milestone A 阶段，最应该避免以下偏差：

1. 过早做复杂前端交互
2. 过早做复杂 fork
3. 过早做复杂 compact
4. 过早做复杂 agent 多步自治
5. 过早把知识结构做得过细

这些方向都可能正确，但不应该抢在知识闭环之前。

## 14. 下一步建议

如果继续往前推进，下一层最自然的文档是：

`将 A1-A6 进一步拆成真正的实现里程碑，例如 A1.1 / A1.2 / A2.1。`

但在进入这一层之前，当前文档已经足以指导一个团队明确：

1. 第一版产品先做什么
2. 什么事情必须后做
3. 怎么判断 Milestone A 已经成立
