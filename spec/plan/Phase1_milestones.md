# Phase 1 里程碑拆分

## 1. 文档目标

本文档基于 [`Implementation_phases.md`](./Implementation_phases.md)，继续将 `Phase 1：跑通核心闭环` 拆成更细的落地里程碑。

本文档解决的问题是：

1. 第一版产品内部应按什么顺序推进
2. 哪些能力必须先出现，哪些能力可以稍后补
3. 每个里程碑需要验证什么
4. 什么时间点可以说“第一版已经成立”

本文档仍然停留在产品和实施顺序层，不展开到工程任务或代码文件级别。

## 2. Phase 1 的总目标

Phase 1 不是要把系统做“全”，而是要把最关键的闭环跑通：

`用户提问 -> 系统判断已有知识是否足够 -> 足够则引用回答，不足则形成待沉淀条目 -> 新内容沉淀为知识节点 -> 后续问题可以复用这些节点`

在此基础上，再补：

1. 基础 fork
2. 基础 symbol registry
3. 基础 compact

因此，Phase 1 应拆成三个递进里程碑：

1. `Milestone A：问答与知识节点闭环`
2. `Milestone B：分支与上下文可控`
3. `Milestone C：长期使用不快速失控`

## 3. Milestone A：问答与知识节点闭环

### 3.1 目标

Milestone A 的目标是：

`证明系统已经不是一次性聊天，而是能把对话结果转成可复用知识节点。`

这是第一版的基础中的基础。

### 3.2 本里程碑必须具备的能力

1. `自然提问入口`
   用户可以直接发起数学问题，不需要先建立复杂结构。

2. `已有知识判断`
   系统能够判断当前问题能否由已有知识回答。

3. `引用式回答`
   当已有知识足够时，系统通过 `summary + detail + hyperlink` 组织回答。

4. `待沉淀条目生成`
   当已有知识不足时，系统先形成一组待沉淀条目，而不是直接无边界生成。

5. `基础知识沉淀`
   回答后新增内容可以进入知识库，至少形成：
   - 标题或主题归属
   - summary
   - detail
   - 基础引用关系

6. `知识树/大纲的最小可见性`
   用户能看到当前已经有哪些节点被沉淀下来。

### 3.3 这一阶段还不要求什么

Milestone A 不要求：

1. 不要求复杂 fork
2. 不要求复杂 compact
3. 不要求复杂符号作用域
4. 不要求复杂结构整理
5. 不要求精细的章节组织

因为这一阶段只验证一件事：

`知识是否真的能从对话中沉淀出来，并在后续被再次用到。`

### 3.4 产品重点

这一阶段要重点盯住的不是回答质量本身，而是“知识闭环”：

1. 提问后系统是否先判断已有知识
2. 系统是否能把新增内容显式化
3. 新内容是否真的成为未来可复用的节点
4. 后续回答是否真的引用这些节点，而不是重新现编

### 3.5 验收标准

Milestone A 完成的标志是：

1. 用户连续问几轮后，知识树中已有稳定新增节点
2. 后续问题可以看到对前面节点的明确引用
3. 当知识不足时，系统会先形成待沉淀条目
4. 用户已经能感受到“这不是普通聊天记录”

## 4. Milestone B：分支与上下文可控

### 4.1 目标

Milestone B 的目标是：

`让用户能围绕局部内容深入，而不把整个系统的上下文拖乱。`

也就是说，从“能积累知识”升级到“能在积累过程中控制复杂度”。

### 4.2 本里程碑必须具备的能力

1. `基础 fork`
   用户可以从回答片段或引用节点继续深入，形成新分支。

2. `分支继承语义起点`
   新分支不继承全部消息，而继承：
   - 当前局部目标
   - 相关节点摘要
   - 必要符号约束
   - 当前焦点片段

3. `基础上下文激活`
   当前会话只激活与当前问题强相关的知识节点。

4. `远处知识降级为摘要`
   远离当前问题的节点不再全量进入上下文，而只保留 summary 级别存在。

5. `局部深入与主线并存`
   用户可以深挖某个点，但不会让主对话完全失去原本主线。

### 4.3 这一阶段仍不要求什么

Milestone B 仍不要求：

1. 不要求复杂分支比较与合并
2. 不要求多层次 branch view
3. 不要求很强的自动 fork 建议
4. 不要求复杂的跨主题桥接

这里先解决“能分叉且不乱”，不解决“分叉管理非常强”。

### 4.4 产品重点

这一阶段最关键的问题是：

1. 系统是否还能保持回答聚焦
2. fork 后用户是否能感受到上下文明显更干净
3. 主线与深入分支是否已经初步分离
4. 多轮使用时是否不再快速爆上下文

### 4.5 验收标准

Milestone B 完成的标志是：

1. 用户可以基于某个引用或片段深挖，而不污染主线
2. 系统能在不同分支中维持不同的局部焦点
3. 回答时不再明显被过多旧上下文拖累
4. fork 已经成为真正可用的产品能力，而不是概念上的按钮

## 5. Milestone C：长期使用不快速失控

### 5.1 目标

Milestone C 的目标是：

`让系统在连续使用一段时间后，仍然保持结构清晰、符号基本一致、知识可复用。`

到了这个阶段，Phase 1 才真正可以上线为“第一版产品”。

### 5.2 本里程碑必须具备的能力

1. `基础 Symbol Registry`
   系统能记录并复用当前重要符号约定。

2. `基础符号冲突处理`
   当新内容和已有约定明显冲突时，系统至少能提示或改写。

3. `基础 /compact`
   `/compact` 至少能做到：
   - 压缩非活跃内容
   - 合并明显重复的小片段
   - 生成长期保留的 summary 视图
   - 对近期新增内容做基础符号对齐

4. `知识结构的初步稳定`
   在连续使用后，知识树不会快速碎裂成不可阅读的片段集合。

5. `系统动作可见`
   用户能够看见：
   - 哪些知识被引用
   - 哪些内容是新增候选
   - compact 做了哪些整理
   - 当前主要符号约束是什么

### 5.3 为什么这一阶段必须放在最后

因为只有在：

1. 知识节点已经开始积累
2. fork 已经开始被使用
3. 上下文复杂度已经显现

之后，compact 和符号一致性的问题才真正会暴露出来。

因此 Milestone C 不应提前做成抽象系统，而应作为对前两个里程碑的稳定化收束。

### 5.4 产品重点

这一阶段重点不是“增加更多功能”，而是验证：

1. 系统会不会越用越乱
2. 数学符号会不会明显漂移
3. compact 是否能真正降低知识碎片化
4. 知识树是否开始具备书稿雏形

### 5.5 验收标准

Milestone C 完成的标志是：

1. 连续使用后，系统结构仍然清晰可读
2. 符号表对回答和沉淀内容已经产生明显约束
3. `/compact` 后结构比压缩前更合理
4. 用户可以把系统当成长期积累数学知识的工具，而不是一次性问答界面

## 6. 三个里程碑之间的依赖关系

### 6.1 Milestone A 是基础

没有 A，就没有真正的知识资产，因此：

1. fork 无从继承有意义的节点
2. compact 无对象可整理
3. symbol registry 也难以发挥真实作用

### 6.2 Milestone B 建立复杂度控制

没有 B，系统即使能积累知识，也会随着深入快速失控，因此：

1. 用户难以长期使用
2. 知识复用会越来越差
3. 后续 compact 会变成被动救火

### 6.3 Milestone C 让第一版真正可上线

没有 C，系统虽然已经“看起来能用”，但会缺少长期稳定性。

因此真正的第一版产品应以 C 完成为边界，而不是 A 或 B。

## 7. 第一版产品的上线判断

如果要定义“什么时候第一版可以上线”，建议标准是：

### 7.1 不能只看 A

因为 A 只证明了系统可以把对话沉淀为节点，但还不能证明系统能长期使用。

### 7.2 也不能只停在 B

因为 B 解决的是分支和上下文问题，但还没有证明系统能长期保持一致性。

### 7.3 应以 C 完成为上线边界

也就是说，第一版产品上线至少应满足：

1. 知识沉淀闭环已经成立
2. fork 已经可用
3. 上下文控制已经具备基本能力
4. 符号一致性已有最低限度保护
5. compact 已能承担基础整理角色

## 8. 推荐推进节奏

### 8.1 先把 A 做到真的可复用

不要在 A 阶段急着做复杂交互。A 的唯一关键是：

`沉淀出的知识节点，后续真的会被再次使用。`

### 8.2 再把 B 做到真的可深入

不要在 B 阶段急着做复杂 branch 管理。B 的唯一关键是：

`用户沿着局部内容深入时，系统仍然保持聚焦。`

### 8.3 最后把 C 做到真的可长期使用

不要把 C 理解成小修小补。C 实际上是第一版能否成立的关键收口：

`系统不会因为连续使用而快速失控。`

## 9. Phase 1 的最终判断

Phase 1 真正完成时，用户应能明显感受到三件事：

1. 这不是普通聊天机器人，因为系统会积累知识
2. 这不是脆弱的上下文堆，因为系统支持分支和局部深入
3. 这不是越用越乱的知识堆，因为系统有基础符号约束和 compact 整理能力

也就是说，Phase 1 的完成状态应是：

`一个已经可以被长期使用的、最小但完整的数学知识演化系统。`

## 10. 下一步文档建议

如果还要继续往前推进，下一层最自然的文档不是再讨论大方向，而是：

`把 Milestone A 再拆成更具体的产品任务顺序。`

原因是：

1. A 是整个 Phase 1 的起点
2. A 的闭环是否成立，决定了后面两层有没有意义
3. 如果 A 拆得不清楚，后面容易一边做交互、一边做智能、一边做整理，最后失焦
